# QA Agent — Decisions

记录你与 QA Agent 已确认、可跨游戏复用的长期质量策略与测试工作方式。具体测试平台和专项范围属于 Game Repository 项目决定。

## 第一轮 QA 工作方式校准
- 测试用例分为 Client 与 Server 两条线；有对应改动时分别维护客户端与服务端测试用例。
- Product 已 `USER_APPROVED` 的 PRD / Acceptance 是功能验收首要事实源；视觉验收同时读取已批准 Art/UI/VFX Artifact。
- 正式编码前 QA 就要形成 `TEST_PLAN.md`，并与 Client/Server `FEATURE_BRIEF.md` 一起作为“开发开工包”提交用户审批；只有两者都通过后才正式编码。
- QA 只执行当前项目/Task 明确纳入范围的平台、网络、性能和回归项，不自动扩大测试范围。
- Bug 分三级：P0 = 功能直接运行阻断；P1 = 功能不符合产品需求预期但不会直接阻断；P2 = 功能符合，但字号、大小、颜色、间距等细节存在问题。
- P0/P1 必须阻塞流程；P2 允许带入下一版本，但必须在 `TEST_REPORT.md` 中向用户明确列出。
- Visual QA 采用固定测试环境、截图/关键帧/短录屏、基线叠加或差异检查，并结合 Art/UI/VFX 专业 Review；自动差异不替代专业视觉判断。

## 待用户确认的两个边界
- QA 建议：服务端严重数据/经济/安全损坏即使页面仍可运行，也升级为 P0，而不是按普通 P1 处理。
- QA 建议：关键视觉效果缺失、关键布局明显偏离批准稿等“重大视觉不符合”按 P1；字号/大小/颜色/间距等细节继续按 P2。

## 可后置到实际项目
- 自动化测试工具链与比例。
- 项目实际平台/设备/浏览器矩阵。
- Visual diff 的具体容差/忽略区域规则。
- 大批量测试用例是否切换到 `.xlsx` 管理。
