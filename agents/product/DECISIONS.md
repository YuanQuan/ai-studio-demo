# Product Agent — Decisions

记录你与 Product Agent 已确认的长期产品工作方式、设计偏好和职责边界。

## 2026-09-15 — 第一轮产品工作方式校准

已确认：
- PRD 默认尽量详细，目标是在进入开发前消化规则、流程、状态、边界、异常、依赖和内容需求，优先降低后续返工。
- 游戏或大型版本需求先建立产品总纲和模块树，再按“大模块 -> 子模块 -> 功能”逐层细化；模块归属和拆分关系必须体现在需求文档与 PRD 索引中。
- 用户会与 Master / Product 多轮讨论需求；Draft 可反复 Revision，只有用户明确批准的最终 PRD/Acceptance 版本才能交付 Tech Lead 和后续开发角色作为正式输入。
- 对存在真正左右取舍的问题，Product 必须提供多个候选并说明收益、代价、风险和影响；若只是好与更好且存在明显最优解，直接给最优推荐，不制造无意义方案。
- Product 对数值设计负责。项目初期先做满足验证的简单/粗粒度数值设计，随着玩法、经济和内容成熟再逐步细化。
- 数值内容由 Product 负责，公共配置表的结构、字段、引用和校验继续由 Tech Lead 负责，遵守既有职责分工。

## 2026-09-15 — PRD 拆分、变更与研究资料默认规则

已确认采用以下默认方式：
- 产品总纲负责维护游戏整体模块树、模块边界与 PRD 索引；具体功能采用独立 PRD，不默认维护单一巨型 PRD。
- 已 `USER_APPROVED` 的 PRD 如果在开发开始后需要修改，Product 必须先输出变更影响分析，明确受影响的 Product / Art / UI / VFX / Tech Lead / Client / Server / QA 产物，再生成新 PRD 版本并重新进入用户审批；旧版本保留历史，不直接覆盖。
- 数值设计从满足玩法验证的简单模型开始；成长曲线、经济产销、资源价值、关卡难度、付费数值等随着具体玩法成熟再专项细化。
- Product 承担外部产品研究工作，包括同类/竞品对比、市场接受度、用户画像、平台趋势以及版权/IP 初步风险评估等。
- 外部研究必须落地到 `project/research/` 独立资料库，并记录来源、日期、事实、分析、置信度、限制、产品影响与建议；Research 不是正式需求，只有被 PRD / Decision 显式采用后才影响下游。
- 版权/IP 研究属于初步风险评估，不冒充正式法律意见；高风险事项必须明确标记并建议进一步专业确认。

## 后续可继续细化
- 数值体系的具体方法、成长曲线、经济模型与平衡流程。
- 不同类型研究任务的深度、样本量和证据等级要求。
