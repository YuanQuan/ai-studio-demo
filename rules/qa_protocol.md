# 两阶段 QA 协议

目标规则版本：`studio-workflow-v2`。集成状态：`PARTIAL_NOT_RELEASED`。相关规则、模板与 Schema 尚未完成一致性接入，详见 `governance/IMPLEMENTATION_STATUS.md`；不能声称新工作流已经完整启用。

以下为已保存的两阶段 QA 设计。产品审批、P0/P1/P2 定义与 Git 权限不因此改变。

## 1. 阶段与触发

- `FUNCTIONAL`：每个功能或相关修复的验收。默认固定本地 Web、测试服务端和测试数据，覆盖功能完整度、异常、关联回归、适用的 Visual QA 与性能验证。
- `RELEASE`：明确进入发布候选阶段后，对具体构建、资源、配置和服务端版本进行上线测试。覆盖声明支持的平台、真机、适用的实际弱网专项，以及平台性能和关键集成回归。
- 保留一个 QA 角色；`test_phase` 与任务 `status` 分离。功能任务 DONE 不代表发布就绪。上线测试 PASS 也不授权上传、部署或发布。
- 不要求普通功能任务执行真机、多平台或实际弱网专项；不得把这些专项偷偷放入 FUNCTIONAL，也不得因此省略异常逻辑测试。

## 2. 功能测试（默认包含性能）

正常流程、边界、状态转换、错误处理、重复操作、相关历史缺陷与受影响集成是测试依据；不机械执行与变更无关的全量回归。

每个功能必须进行性能适用性评估，并在开发开工包中确定场景、环境、基线、指标、阈值与测量方法。Tech Lead 组织性能预算，Client/Server 提供实现与测量支持，QA 验证，Product 提供体验目标。

按功能选取指标：
- UI/列表：打开耗时、交互或滚动卡顿、重复进入退出与释放。
- 战斗/动画/VFX：帧时间及峰值、并发效果、节点/事件/计时器、对象分配与资源增长。
- 资源：首次/重复加载、缓存、释放与残留。
- 服务端：延迟分布、查询次数、重复请求、受控负载、资源占用（本功能有服务端时）。

项目数值存于 `project/quality/PERFORMANCE_BUDGET.md`；不能把某游戏阈值升级为所有游戏的硬标准。基线未确定或必要环境不可用时标记 NOT_TESTED/BLOCKED，不能用编译通过、代码审查或主观流畅替代实测。单项不适用需注明理由和审查依据；不能用总体 N/A 绕过性能适用性评估。

测量记录应包含运行版本、环境、测试数据/负载、采样/重复方法、测量结果、阈值与证据路径。性能不达标阻止对应验收；缺陷等级仍沿用已经批准的定义，不自行改级。

功能阶段可以用受控输入测试超时、失败、重复响应和恢复状态的业务行为。此类测试不等于真实弱网、网络栈或平台兼容性已验证。

## 3. 上线测试

进入 RELEASE 前必须指定候选构建与哈希、资源/配置/服务端版本、发布平台矩阵和设备范围。不得用一个模糊的“最新版”覆盖不同包。

至少检查声明平台上的启动、生命周期、核心流程、屏幕适配和实际设备表现；涉及的登录/广告/支付/网络能力按已批准发布范围验证。实际弱网覆盖适用的延迟、抖动、限速、丢包、断线、重连/恢复和重复操作风险。

纯离线产品的弱网等不适用项须在发布矩阵中保留 N/A 理由与审查记录；不能因为缺少设备、账号或测试工具就改为不适用。缺失必要资源记 BLOCKED，可继续不受影响的功能工作。

上线测试复用有效的功能证据，并执行平台差异、变更影响和关键跨功能回归，不机械从头重写全部用例。Web 性能结果不能代替真机性能结论。

候选构建、相关配置、资产或服务端发生变化后，旧结论不得无条件继承；QA 做影响分析并重测受影响项。未通过全部必需范围时不得显示 RELEASE_READY。

## 4. 交付与门禁

沿用 TEST_PLAN.md / TEST_REPORT.md，必须明确 FUNCTIONAL 或 RELEASE、Task ID、规则版本、输入 Artifact 版本、目标版本/哈希、环境、覆盖/排除范围、缺陷及证据。可将性能和平台矩阵放入同一文档的章节，避免重复文档。

- FUNCTIONAL：Client/Server 用例按适用范围维护；功能、视觉和性能结果分别展示。整体 PASS 必须具有必要的实际验证证据。
- RELEASE：额外提供候选版本和平台/真机/弱网矩阵；平台未测或关键项阻塞不能汇总成通过。
- 结构化摘要使用 `schemas/v2/test_report.schema.json`；正式文字报告与证据通过路径关联。
- P0/P1 必须关闭；P2 可延期但须记录。不得为了通过而删用例、改期望、放宽阈值或隐藏未测项。
- 正式游戏产物仍按原有用户审批门禁执行；QA 阶段变化不授权绕过实施报告审批或代替用户最终验收。

## 5. 旧项目迁移

已有已批准测试计划和历史结果保持不变，不回填新测试为 PASS。新任务使用 v2；在执行任务固定旧规则，下一安全交接点建立差异补充计划后切换，不改写原审批记录。补充计划仍遵守游戏产物审批；性能预算不明时由 Tech Lead/QA 提出并落盘。

既有功能 DONE 不被悄悄撤销；发布时不能把旧功能验收当作新上线结论。迁移状态、下一动作和未测项必须出现在会话恢复索引与 Dashboard。
